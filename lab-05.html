Configure SSL Inspection Policies

Enable TLS inspection, verify the Zscaler CA, and handle a certificate-pinning application.

Time: ~30 minutesTasks: 3Outcome: Encrypted traffic inspected with a targeted bypass
Technical concept

What SSL/TLS inspection is doing

HTTPS protects data in transit, but encryption also hides content from security controls. ZIA TLS inspection creates two encrypted sessions so it can decrypt, inspect, apply policy, and then re-encrypt the traffic.

User / browserTrusts the inspection CA
TLS session 1→
ZIA Service EdgeDecrypt → inspect → enforce → re-encrypt
TLS session 2→
DestinationOriginal server certificate
Why inspect?

Security needs visibility

Inspection lets ZIA evaluate encrypted web traffic for threats, data protection, and other content-aware policies.

Certificates

The endpoint must trust the inspection CA

ZIA presents a dynamically issued inspection certificate to the client. In this lab, Client Connector deploys the trusted Zscaler CA according to the App Profile.

Certificate pinning

Some apps reject replacement certificates

A pinned application expects a specific certificate or key. The ZIA-issued inspection certificate does not match, so the app may fail. The normal fix is a targeted Do Not Inspect rule, not a broad bypass.

i
What you will prove in Lab 5

First compare the certificate before and after inspection, then optionally verify the trusted root CA, and finally reproduce a certificate-pinning failure and bypass only the affected application.

5.1

Enable SSL Inspection for All Destinations

Turn on TLS inspection for encrypted traffic and confirm the certificate chain changes.

Experience Center · find this resource
Internet Access›Policy›SSL/TLS Inspection

Search Menu → SSL/TLS Inspection

Official documentation: SSL/TLS Inspection Policy

  1. Before the policy change, open an Incognito Chrome window to https://www.wikipedia.org and inspect the site certificate. Note the original server certificate issuer.
  2. Open
    Internet Access›Policy›SSL/TLS Inspection
    Select Add SSL Inspection Rule.
  3. Configure Rule Order 1, Rule Name SSL Inspect All, and Action Inspect. Save and Activate.
  4. Close/reopen Incognito (or refresh), revisit Wikipedia, and inspect the certificate again. It should now be signed through Zscaler.
i
Correlate the TLS inspection policy

Alongside the browser certificate-issuer change, use Web Insights → Logs for a transaction from the test browser/timeframe and check the SSL/TLS inspection decision or policy reason where available. Certificate-chain evidence and a matching rule together better support the conclusion that inspection was applied.

✓
Expected result

HTTPS traffic matches SSL Inspect All and the browser sees a Zscaler-issued inspection certificate.

Technical deep dive · before Task 5.3

Why certificate pinning can break TLS inspection

Certificate pinning adds an application-level trust check on top of normal certificate validation. Instead of accepting any server certificate that chains to a trusted CA, the application expects a particular certificate, public key, or approved set of pins for its back-end service.

Why applications pin certificates

Extra protection against impersonation

Pinning is intended to make man-in-the-middle attacks harder—even if an attacker can present a certificate that the operating system would normally trust. The application performs its own additional comparison against the expected certificate or key.

The trade-off is operational rigidity: certificate rotation, back-end changes, or enterprise TLS interception can break the application unless the pin set or application behavior is updated.

Why ZIA cannot simply label it “certificate pinning”

The client does not send a pinning-specific error

ZIA sees the client terminate or fail the TLS handshake, but the application does not send a standard message that says “certificate pinning detected.” Different clients can fail in different ways.

Treat handshake-failure log reasons as evidence to investigate, not as a definitive certificate-pinning signature.

How to resolve it

Prefer the narrowest supported exception

  • Confirm that TLS inspection is the condition that triggers the application failure.
  • If the application/vendor supports an inspection-compatible enterprise option, prefer that supported design.
  • Otherwise create a targeted Do Not Inspect rule for the specific cloud application or required domains.
  • Avoid broad category, user, or global bypasses simply to make one pinned application work.
Security implication of bypassing

You restore application compatibility, but lose decrypted-content visibility

The application keeps end-to-end TLS and its pinning protection, but ZIA no longer decrypts that flow. Security controls that require inspection of the encrypted payload therefore lose that visibility for the bypassed traffic.

Design principle: bypass only what is necessary, document the business reason, and keep the exception as narrow as practical.

!
Important troubleshooting distinction

A trusted Zscaler inspection CA does not guarantee that a pinned application will accept the connection. Normal OS trust and application-level pin validation are two different checks.

5.3

Review Certificate Pinning Errors

Reproduce a TLS-handshake failure with a certificate-pinned application, investigate the symptoms in Web Insights, then apply a targeted inspection bypass.

Experience Center · find this resource

Search Menu → Web Insights

  1. On Corp Client PC, download Threema Private Desktop for Windows from https://threema.com/en/download/threema-private.
  2. Install the downloaded MSIX from PowerShell with Add-AppxPackage -Path .\Downloads\threema-desktop-latest-windows-x64.msix

    If the downloaded filename is different, substitute the actual MSIX filename.

  3. Launch Threema Private / Threema Beta after the installation completes. Installing the package alone does not generate the test condition.
  4. With the SSL Inspect All rule still active, wait for Threema to attempt its back-end connection. Observe the connection failure.
  1. Open Web Insights → Logs. Set a recent timeframe that includes your Threema test and filter on your lab user if needed.
  2. Add the filter Client SSL/TLS Handshake Failure Reason. Check for one or more of these values:
    Unknown CAClose Notify or Client TCP ResetCertificate UnknownBad or Unsupported CertificateBad Record MacHandshake Failure
    !
    These are symptoms, not proof of certificate pinning

    ZIA cannot directly identify certificate pinning. A pinned client can terminate the handshake in different ways, so use these values to find relevant failed TLS sessions and correlate them with the application failure.

  1. As a second view, use SSL/TLS Policy Reason and look for Not inspected because of failed client SSL/TLS handshake.
  1. Return to
    Internet Access›Policy›SSL/TLS Inspection
    Add a rule at order 1 named Bypass Threema. Under Cloud Applications, select Instant Messaging → Threema. Set Action to Do Not Inspect, then Save and Activate.
  2. End any running Threema process in Task Manager, then reopen the application so it establishes a fresh TLS session.
  3. Confirm that Threema now connects. The targeted bypass allows the application to see its original server certificate/key instead of the ZIA-issued inspection certificate.
i
Keep the exception narrow

Do not disable TLS inspection globally to solve a single pinned application. Use the smallest practical Cloud Application or domain scope and retain the business justification for the exception.

i
Evidence-based TLS diagnosis

Record the Threema failure time, the matching handshake-failure evidence in Web Insights, and whether connectivity returns only after the narrow Bypass Threema / Do Not Inspect policy is activated. This correlation supports an inspection incompatibility consistent with pinning, but a generic TLS handshake failure is not definitive proof of certificate pinning. Confirm the bypass rule or not-inspected policy reason when the log fields are available.

✓
Expected result

Threema fails while TLS inspection is active; Web Insights shows client-handshake failure symptoms that correlate with the test; after the targeted Do Not Inspect rule is activated and the app is restarted, Threema connects successfully.
