Technical concept

What SSL/TLS inspection is doing

HTTPS protects data in transit, but encryption also hides content from security controls. ZIA TLS inspection creates two encrypted sessions so it can decrypt, inspect, apply policy, and then re-encrypt the traffic.

Why inspect?

Security needs visibility

Inspection lets ZIA evaluate encrypted web traffic for threats, data protection, and other content-aware policies.

Certificates

The endpoint must trust the inspection CA

ZIA presents a dynamically issued inspection certificate to the client. In this lab, Client Connector deploys the trusted Zscaler CA according to the App Profile.

Certificate pinning

Some apps reject replacement certificates

A pinned application expects a specific certificate or key. The ZIA-issued inspection certificate does not match, so the app may fail. Confirm the cause before using a narrowly scoped Do Not Inspect exception; understand the visibility tradeoff below.

Certificate pinning: trust is only the first check

Ordinary TLS certificate validation checks the server name, validity period, and chain to a trusted certification authority (CA). Pinning adds an application-controlled restriction: the certificate or public key must match an expected value (often a stored hash). A valid, trusted certificate can therefore still be rejected. Pins may refer to a leaf certificate, a public key, or a CA in the chain; the application's implementation determines what is accepted.

Direct TLS

Original identity

Server presents its real certificate → normal validation passes → expected pin matches → app connects.

Inspected TLS

Replacement identity

ZIA presents its inspection certificate → CA trust may pass → pinned certificate or key differs → app rejects the connection.

Targeted Do Not Inspect

Original identity preserved

ZIA passes the encrypted connection without replacing the certificate → app can validate the server and its pin → connection can succeed.

During inspection, ZIA terminates the client's TLS connection and creates a separate connection to the destination. Its generated certificate can contain the correct hostname, but it does not carry the destination's pinned identity. ZIA does not possess the destination's private key. Installing the inspection root CA fixes a missing trust anchor; it does not make a replacement certificate match an application's pin. The app may stop during the handshake or close the connection afterward, showing only a generic network or WebSocket error. Zscaler: pinning and inspection.

Why applications pin certificates

Pinning narrows which server identities an app accepts, helping resist impersonation even if an unexpected CA becomes trusted or a certificate is misissued. The same restriction can reject an organization's authorized inspection proxy. Pins also create an availability obligation: certificate/key rotation and app updates must be coordinated or legitimate connections may fail. Pinning should remain under the application vendor's control. OWASP: pinning design and operational risks.

Diagnose first, remediate safely

  • Establish the cause. Correlate the app version, error time, user, destination and logs. Check device time, certificate expiry, CA deployment and the app's own trust store, plus DNS, connectivity and TLS compatibility. A handshake failure alone does not prove pinning.
  • Use a controlled comparison. With the same client and destination, compare inspection enabled with a temporary, approved exception. Success without inspection supports an inspection compatibility issue; confirm pinning using vendor documentation or diagnostics. Threema documents TLS pinning in its Desktop 2.0 release history.
  • Choose the smallest supported exception. For confirmed pinning, scope Do Not Inspect to the affected app and intended users/devices or locations where supported. Place it above the general Inspect rule and activate it. Confirm the actual endpoints match; do not guess broad domain wildcards. See SSL/TLS inspection policy configuration.
  • Prevent repeat incidents. Pilot app updates and inspection changes, document the exception's owner and business need, review it periodically, and use vendor-supported fixes when available. If the risk is unacceptable, block the app or provide an approved alternative.
i
Security tradeoff: connectivity versus content visibility

Do Not Inspect preserves encrypted transport and the app's pin validation, but ZIA cannot inspect the encrypted payload for malware or sensitive data. Controls that rely on decrypted content lose visibility for that traffic; metadata-based controls depend on what remains observable and on policy. Keep endpoint protection, application governance and monitoring in place. This is an inspection exception, not an instruction to bypass traffic forwarding or disable Client Connector.

Never use “accept all certificates,” disable server verification, patch out pin checks, or turn off inspection globally as a troubleshooting fix. TLS inspection also does not inherently decrypt an application's separate end-to-end message encryption.

5.1

Enable SSL/TLS Inspection for All Destinations

Turn on TLS inspection for encrypted traffic and confirm the certificate chain changes.

Current Experience Center navigation
Internet Access›Policy›SSL/TLS Inspection
  1. Before the policy change, open an Incognito Chrome window to https://www.wikipedia.org and inspect the site certificate. Note the original server certificate issuer.
  2. Open
    Internet Access›Policy›SSL/TLS Inspection
    Select Add SSL Inspection Rule.
  3. Configure Rule Order 1, Rule Name SSL Inspect All, and Action Inspect. Save and Activate.
  4. Close/reopen Incognito (or refresh), revisit Wikipedia, and inspect the certificate again. It should now be signed through Zscaler.
✓
Expected result

HTTPS traffic matches SSL Inspect All and the browser sees a Zscaler-issued inspection certificate.

5.3

Review Certificate Pinning Errors

Reproduce a certificate-pinning failure, bypass inspection only for the affected application, then verify the transaction logs.

Current Experience Center navigation
Internet Access›Policy›SSL/TLS Inspection

Fastest option: use Search menu and search for Web Insights.

  1. On Corp: Client PC, download the Windows Desktop App 2.0 (Beta) MSIX from https://threema.com/en/download/threema-private. Use the desktop app, not the browser client.
  2. Install the downloaded MSIX in PowerShell: Add-AppxPackage -Path "$env:USERPROFILE\Downloads\threema-desktop-latest-windows-x64.msix" Adjust the filename/path if your download differs. Wait for installation to finish; installing alone does not generate the app's connection error.
  3. Launch Threema Beta from the Windows Start menu while TLS inspection is active. Allow the app to attempt its connection/linking flow. Observe any Connection Error, expand Show Technical Details, and record the time. The supplied example shows a RendezvousConnection / WebSocket error. A PowerShell installation error is a separate issue; resolve it before continuing. Completing account linking requires the mobile Threema app, but do not confuse account setup with TLS connectivity.
  4. Open Web Insights → Logs using Experience Center search. Select a timeframe covering the launch attempt and your own lab user. Allow several minutes for logs to arrive. Use the filters below to find candidate failures; correlate the URL with Threema and the recorded time before changing policy.
  5. Open Internet Access → Policy → SSL/TLS Inspection. Add a rule at order 1, above SSL Inspect All, named Bypass Threema. Under Cloud Applications, choose Instant Messaging → Threema; set Action to Do Not Inspect. Limit scope to the intended lab users/location where available. Save and Activate.
  6. End any running Threema process in Task Manager and reopen Threema Beta. Retry the same connection/linking action and record the new time. The earlier TLS-related connection error should no longer prevent progress if the rule matches the affected traffic.
  7. Return to Web Insights → Logs. Retain the before-change evidence, then query the new attempt separately. Check whether the same destination failures recur. Clear failure-only filters to examine any available new transactions and verify the matching inspection exception in the transaction details. An empty failure search alone is not proof of success: combine app behavior with fresh, correlated traffic evidence. If failures persist, check activation, rule order, app/destination matching and other connectivity causes.

  • Handshake Failure

SSL/TLS Policy Reason

In a separate search, look for Not inspected because of failed client SSL/TLS handshake.

These are possible symptoms, not a definitive pinning signature. ZIA cannot directly identify certificate pinning, and clients may fail the handshake in different ways. These reasons can also have other causes. The policy reason describes a failed handshake; it does not mean a successful Do Not Inspect exception was applied.
