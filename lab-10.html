Technical context · after Lab 10

How application segments and access policies work together

A working private application needs two independent things: the correct application match (destination, protocol, and port) and a matching access policy that allows the user. An Allow policy cannot compensate for a port missing from the selected application segment.

1 · Wildcard and specific domains

In this lab, the Discovery segment broadly covers *.patraining.safemarch.com, while the Intranet segment identifies intranet.patraining.safemarch.com. Under ZPA's default Exact Match behavior, the more specific FQDN takes precedence. Defining the Intranet host separately does not make it inherit every port or access permission from Discovery.

SegmentDomainPractical implication
Discovery*.patraining.safemarch.comGeneral discovery / policy coverage for matching subdomains not taken by a more specific segment.
Intranetintranet.patraining.safemarch.comSeparate protocol, port, App Connector group, and access-policy requirements for this application.

2 · Access policy order

When a traffic request identifies an application, ZPA evaluates matching Access Policy rules in priority order (top down). The first rule whose application and other required conditions match decides the action. Later rules do not override an earlier match; if no Allow rule applies, access is implicitly denied.

PriorityIllustrative ruleAction
1Block contractors accessing IntranetBlock
2Allow approved employees accessing IntranetAllow
3Allow users to general private applicationsAllow

Why order matters: A broad Allow all users / all applications rule placed above the contractor restriction can match first, making the restrictive rule ineffective. Application specificity and access-rule order are related, but not the same decision.

3 · Real-world scenarios

AttemptWhat to expect / investigate
Intranet on TCP 80Matches the specific Intranet segment's configured port; applicable access policy and entitlement must still allow the user.
Another host under *.patraining.safemarch.comMay match Discovery if its protocol/port and the relevant policy permit it.
Intranet on TCP 3389, but the Intranet segment lists only TCP 80With default Exact Match, the more specific Intranet segment wins; the client can drop the request rather than falling back to Discovery—even if Discovery lists 3389. Such attempts may not appear in ZPA cloud diagnostic logs.
A broad Allow rule appears above a restrictive Block ruleThe earlier Allow can take precedence if it matches; review rule order and the matched criteria.
A user's ZPA entitlement is missingAccess fails even if the application segment and policy appear correct (the scenario explored in Lab 11).
ICMP is not enabled for the selected segmentPing may fail even though the web application itself is reachable; verify ICMP independently of TCP access.

4 · What about Application Segment Multimatch?

Multimatch is an optional, version- and feature-dependent capability that can allow a wildcard segment to cover ports omitted from the more specific FQDN segment. It is not the default and should only be enabled after checking its prerequisites and feature conflicts. For this lab, keep the focus on explicitly defining the correct ports on the intended segment.

Troubleshooting order: confirm the destination FQDN/IP and most-specific segment → check protocol/port and optional ICMP setting → review Access Policy match and rule order → verify user entitlement and App Connector reachability. Lab 11 explores entitlement failure; optional Lab 13 demonstrates the RDP port-mismatch case.
