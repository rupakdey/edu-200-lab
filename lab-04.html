Lab 4

Configure Firewall Filtering Policy

Observe the default block, allow required non-web traffic, and restrict an application.

Time: ~25 minutesTasks: 3Outcome: ICMP/SSH allowed; WhatsApp blocked
4.1

Test Non-Web Traffic with the Default Firewall Block

Confirm that the default firewall behavior blocks unmatched non-web traffic.

Experience Center · find this resource

Search Menu → Firewall Control

i
How the Default Firewall Filtering Rule works

With Z-Tunnel 2.0, non-web traffic is forwarded to Zscaler and evaluated against firewall rules in priority order. Earlier rules can explicitly allow required traffic (such as Zscaler proxy services or approved application traffic); the Default Rule is the final catch-all and is configured to Block/Drop anything that has not matched an applicable Allow rule.

In this task: outbound ICMP (ping) and SSH (TCP 22) do not match the existing Allow exceptions, so the Default Rule drops them. In Task 4.2 you will add explicit Allow rules and retest. The default rule itself does not grant web access; permitted web/proxy traffic is handled by applicable earlier rules and services.

  1. Open
    Internet Access›Policy›Firewall Control
    Verify the Default Rule is Block/Drop and that no earlier rule permits the ICMP/SSH tests used below.
  2. On Corp Client PC run ping www.google.com. The request should time out.
  3. Open PuTTY, set Host Name to github.com, and click Open. The outbound SSH connection should time out/fail.
  4. Close PuTTY and Command Prompt.
i
Verify the policy cause, not just the symptom

When Firewall Insights or Firewall Insights Logs are available, filter the same test timeframe and student user. Compare the blocked ICMP/SSH attempts with the Default Firewall Filtering Rule and action Block/Drop. A ping timeout or SSH failure alone is not conclusive; if logs are absent, confirm traffic was forwarded to ZIA and that firewall logging is enabled.

✓
Expected result

ICMP and SSH fail because they fall through to the default Block/Drop rule.

4.2

Configure Firewall Policy to Allow Outbound SSH and ICMP Traffic

Add one rule that allows outbound ICMP and SSH for the student user.

Experience Center · find this resource
Internet Access›Policy›Firewall Control

Search Menu → Firewall Control

Official documentation: Firewall Filtering

  1. In
    Internet Access›Policy›Firewall Control
    select Add Firewall Filtering Rule.
  2. Configure:
    SettingValue
    Rule Order1
    Rule StatusEnabled
    Rule NameICMP_SSH
    UserStudent Admin
    Network ServicesICMP, SSH
    Network TrafficAllow
    Save and Activate.
  3. On Corp Client PC run ping www.google.com again. It should now receive replies.
  4. Open PuTTY to github.com. A server-key/login prompt is enough to prove TCP/22 is reaching the destination; you do not need to authenticate.
i
Corroborate the Allow rule

Where firewall logs are available, filter by the test user and ICMP_SSH rule. Look for Allow on ICMP and TCP 22 after activation. The PuTTY server-key prompt is a useful connectivity signal, but correlate it with the rule hit when possible.

✓
Expected result

ICMP succeeds and PuTTY reaches the SSH server.

4.3

Configure a Firewall Filtering Policy to Restrict Applications

Configure a WhatsApp network-application firewall rule and verify whether matching traffic is classified and blocked.

Experience Center · find this resource
Internet Access›Policy›Firewall Control

Search Menu → Firewall Control

Official documentation: Firewall Filtering

  1. In
    Internet Access›Policy›Firewall Control
    add a Firewall Filtering Rule.
  2. Configure:
    SettingValue
    Rule Order2
    Rule StatusEnabled
    Rule NameRestrict_Whatsapp
    UserStudent Admin
    Network ApplicationWhatsApp
    Network TrafficBlock/Drop
    Save and Activate.

  3. After activating the rule, browse to https://web.whatsapp.com. Observe whether access succeeds or is restricted. If blocked, verify the matching rule in Firewall Insights before concluding that Restrict_Whatsapp caused the result.

i
Technical context — WhatsApp web and network-application rules

ZIA Advanced Firewall uses deep packet inspection (DPI) to identify supported network applications, but a rule matches only traffic that reaches the relevant inspection path and is successfully identified as WhatsApp. WhatsApp Web may also be affected by URL Filtering or Cloud App Control; these can apply to HTTP/HTTPS traffic from browsers and other clients. This rule does not guarantee blocking of every browser, desktop, or mobile WhatsApp connection. A failed browser page alone does not identify the policy responsible.

i
Confirm the matching firewall rule

In Firewall Insights/Logs, narrow the timeframe to the WhatsApp test and look for Restrict_Whatsapp with a blocking action. If the application fails without a matching event, check network application identification, other ZIA rules, and client state before attributing the failure to this policy.

✓
Expected result

The Restrict_Whatsapp firewall rule is configured and tested. Attribute a blocked WhatsApp connection to this rule only if Firewall Insights shows a corresponding Restrict_Whatsapp event with a Block/Drop action; a failed web page alone is not proof.

✓
Lab 4 complete

ICMP/SSH allowed; WhatsApp network-application rule configured and evaluated using matching firewall events.
