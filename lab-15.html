Troubleshoot Poor Wi-Fi

Use user telemetry, Y-Engine, Cloud Path, and device events to isolate a Wi-Fi issue.

Time: ~15 minutesTasks: 5Outcome: Wi-Fi change correlated to poor ZDX scoreEnvironment: SDC · read-only

Labs 14–16 use the pre-configured SDC tenant, not your learner tenant. Complete the SDC access checkpoint before continuing. Do not create or modify configuration unless a lab step explicitly instructs you to.

15.1

View User ZDX Score for an Application

Find Curtis Hardwick and isolate the period/application associated with the Wi-Fi complaint.

Experience Center · find this resource

Search Menu → Users Overview

  1. In Digital Experience use Search menu for User/Device Search → User Search. Search for Curtis Hardwick and open the result.
  2. Reset any filters left from Lab 14.
  3. Set the incident range to approximately 48 Hours, select Salesforce Lightning, and review ZDX Score Over Time. Look for frequent transitions between Good and Poor.
i
Keep in mind

If the standard 48-hour view does not show a useful pattern, use a custom reporting window.

✓
Expected result

Curtis Hardwick’s Salesforce Lightning score shows a usable incident window with Good/Poor transitions.

15.2

Analyze Poor ZDX Score Interval

Use Y-Engine Analyze Score on a poor sample to identify likely contributors.

Experience Center · find this resource

Search Menu → ZDX Score

  1. On ZDX Score Over Time, zoom around a period where the score is Poor. Include some time before and after the degradation.
  2. Select a Poor point, note its score, and click Analyze Score.
  3. Review the factor table and identify the strongest contributors. In the source scenario, low/suboptimal Wi-Fi is a common result.
i
Keep in mind

The SDC traffic is simulated; exact scores, SSID names, and contributing factors can differ from the source screenshots.

✓
Expected result

Y-Engine provides a ranked explanation of factors contributing to the poor sample.

15.3

Compare Poor ZDX Score to Last Known Good Score

Compare the poor sample with the last known good sample.

Experience Center · find this resource

Search Menu → ZDX Score

  1. With the Poor data point selected, click Compare to → Last known good score.
  2. Compare the analyzed vs comparison points, especially ZDX Score, Wi-Fi identifier/SSID, and Client-Egress Latency.
✓
Expected result

The comparison highlights what changed between a good experience and the selected poor interval.

15.4

Isolate High Latency Hop

Use Cloud Path and Hop View to determine where the added latency begins.

Experience Center · find this resource

Search Menu → Cloud Path Probe

  1. Return from Compare ZDX Scores to Curtis Hardwick’s user view and keep Salesforce Lightning selected.
  2. Zoom again into a Poor score interval and scroll to the Cloud Path latency graph.
  3. At the selected sample, inspect Hop View and identify the hop contributing the largest end-to-end latency.
  4. If no hop data exists for the selected point, choose another sample with data. A complete outage can leave no path telemetry.
✓
Expected result

You can identify whether latency starts at the first/local hop or later in the path.

15.5

View User Device Events Associated with ZDX Score Changes

Correlate network-interface events with the score degradation and recovery.

Experience Center · find this resource

Search Menu → Device Events

  1. In the same user/time view, scroll to User Device Events.
  2. On the Network timeline, find the time when the ZDX score became Poor. Hover the corresponding event dot and review Network Interface fields, especially New Value.
  3. Repeat for the recovery back to Good. Compare SSID changes, disconnects, and signal changes with the score trend.
  4. Form a root-cause statement from the correlation. The source scenario associates SSID changes/poor Wi-Fi with the poor experience.
✓
Expected result

Device events and Wi-Fi changes support the root-cause conclusion for Curtis’s degraded experience.

✓
Lab 15 complete

Wi-Fi change correlated to poor ZDX score
