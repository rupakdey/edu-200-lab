Technical context

How Source IP Anchoring changes the traffic path

Most ZIA traffic is inspected by a ZIA Service Edge and then exits to the internet from a Zscaler public IP. That works for normal internet access, but some SaaS, partner, and public applications only accept connections from an approved corporate public IP. SIPA solves that requirement for selected applications without giving up ZIA security inspection.

Why this lab uses both ZIA and ZPA

SIPA connects policy decisions in the two services:

  1. ZIA inspects the traffic and matches the destination against the SIPA forwarding rule.
  2. ZIA forwards the selected flow to ZPA instead of sending it directly to the normal Zscaler internet egress.
  3. ZPA delivers the flow to the selected App Connector in the organization-controlled environment.
  4. The organization’s NAT/firewall provides the public egress IP that the destination sees and can allowlist.

What to remember before you configure

  • Only policy-selected applications use SIPA. Other internet traffic continues through the regular ZIA path.
  • The destination sees the organization-controlled public NAT IP, not the endpoint private IP and not the normal Zscaler public egress IP.
  • SIPA is about source-IP presentation, not authentication. Application authentication and other access controls still apply.
  • The ZPA Gateway used by ZIA is a forwarding configuration that links the ZIA rule to the ZPA delivery path; it is not an additional customer appliance.
i
The goal of Lab 12

You will first establish the normal/native and ZIA egress behavior, then build the ZPA SIPA objects, connect them to a ZIA Forwarding Control rule, and finally verify that only the selected public application leaves through the anchored corporate egress.

12.1

Configure Source IP Anchoring in ZPA

Configure the ZPA side of Source IP Anchoring, including the SIPA application and forwarding policies.

Current Experience Center navigation
Private Access

Fastest option: use Search menu and search for Defined Application Segments / Access Policy / Client Forwarding Policies.

  1. On Corp: Client PC temporarily disable ZIA and ZPA in ZCC, browse to https://ip.zscaler.com, and note the native public IP. Re-enable ZIA/ZPA and repeat to note the normal ZIA egress IP.
  2. Open
    Infrastructure›Private Access›App Connectors
    and confirm an App Connector is connected.
  3. In Private Access open
    Policies›Access Control›Private Applications›Defined Application Segments
    Add:
    SettingValue
    NameSIPA Application
    Source IP AnchorEnabled
    Applicationip.zscaler.com
    TCP Ports80, 443
    Segment GroupSIPA Segment (Enabled)
    Server GroupSIPA Server
    App Connector GroupOnPrem
    Save.
  4. Create Access Policy SIPA Policy with Action = Allow Access and criteria mapped to the SIPA application/segment group. Save.
  5. Open
    Infrastructure›Private Access›Client Connector Policies›Client Forwarding Policies
    Add SIPA Bypass: Action = Bypass ZPA, applications = SIPA application/segment group, Client Type = Client Connector. Save.
  6. Add SIPA Forward: Action = Forward to ZPA, same application/segment mapping, Client Type = ZIA Service Edge. Save.
✓
Expected result

ZPA has a SIPA-enabled application segment plus the access/client-forwarding policy needed for source anchoring.

12.2

Configure ZIA Forwarding for SIPA

Create the Private Access gateway first, then create the Forwarding Control rule that sends the SIPA application through that gateway.

i
Two ZIA objects are required

Private Access GW maps ZIA to the SIPA-enabled ZPA server group/application segment. Forwarding Control then selects matching traffic and sends it to that gateway.

  1. Open the Private Access gateway configuration:
    Infrastructure›Internet & SaaS›Private Access GW

    You can also use the Experience Center search and search for Private Access GW.

  2. Click Add Gateway for ZPA / Add Private Access Gateway and configure:
    SettingValue
    Gateway NameSIPA Gateway
    Server GroupSIPA Server
    Application SegmentSIPA Application
    DescriptionOptional

    After selecting the SIPA server group, the associated SIPA-enabled application segment should be available for selection.

  3. Save the Private Access gateway and Activate the change.
!
Quick troubleshooting: Server Group not available?

If SIPA Server is not visible when creating the Private Access gateway, return to the ZPA application segment and verify that SIPA Application has Source IP Anchor = Enabled. This is required for the SIPA server group/application segment to be surfaced for the gateway configuration.

  1. Open:
    Internet Access›Policy›Forwarding Control
    Click Add Forwarding Rule.
  2. Configure the SIPA forwarding rule:
    SettingValue
    Rule NameSIPA Forward
    Rule StatusEnabled
    Forwarding MethodZPA
    Application Segment / DestinationSIPA Application
    Forward to ZPA GatewaySIPA Gateway
  3. Save the forwarding rule and Activate the change.
i
Why the order matters

The Forwarding Control rule can only send SIPA traffic to a usable ZPA gateway after the Private Access GW object exists and is mapped to the correct SIPA-enabled server group/application segment.

Official reference: Configuring Private Access Gateway.

✓
Expected result

SIPA Gateway maps ZIA to the SIPA-enabled ZPA objects, and the SIPA Forward rule sends traffic matching SIPA Application to that gateway.

12.3

Verify SIPA Functionality

Prove that the selected destination uses the anchored path, then move the SIPA mapping to another domain.

Current Experience Center navigation
Private Access›Policies›Access Control›Private Applications›Defined Application Segments
  1. On Corp: Client PC browse to https://ip.zscaler.com and record the displayed public IP. It should differ from the normal ZIA egress observed at the start of Lab 12.
  2. Edit the SIPA Application segment in Private Access. Remove ip.zscaler.com and add ping.eu instead; save.
  3. Browse to https://ping.eu and observe the public IP. Traffic for the newly defined application should now use the ZPA-SIPA egress path.
✓
Expected result

The anchored egress follows whichever public application is currently mapped into the SIPA Application segment.

✓
Lab 12 complete

Selected public app egresses through a fixed SIPA path
